# Механизм эмуляции платежа — кейс 3 (заполнено и сверено с эталоном)

## 1. Состояния платежа (5 состояний)

* **`CREATED`** — платёж инициализирован в Платформе после выбора процента чаевых клиентом (Экран 2 → Экран 3), суммы `tip_amount` и `amount_total` зафиксированы, но запрос в платёжный шлюз ещё не отправлен. Из этого состояния клиент может штатно отменить платёж (`CANCELED`).
* **`PENDING`** — клиент нажал «Подтвердить оплату», транзакция отправлена в платёжный шлюз и ожидает ответа эквайера (либо осталась в этом статусе при таймауте шлюза `h == 9` / `GATEWAY_TIMEOUT` до фоновой сверки). Отмена клиентом из этого статуса запрещена (`409 CANCEL_NOT_ALLOWED`).
* **`SUCCESS`** — терминальный (финальный) успешный статус: платёжный шлюз подтвердил списание средств (`h in 0..7`), одноразовый `nonce` QR-кода погашен, сумма чаевых зачислена в отчётность официанта и ресторана.
* **`DECLINED`** — терминальный статус отказа: платёжный шлюз отклонил операцию (`h == 8`, например, недостаточно средств или блокировка карты — `CARD_DECLINED`, HTTP 402). Деньги не списаны; клиент может повторить попытку с другой картой.
* **`CANCELED`** — терминальный статус отмены: клиент самостоятельно отменил платёж на Экране 3 до его отправки в шлюз (переход `CREATED` → `CANCELED`). Деньги не списывались.

| `PENDING` | `PENDING` | Эмулятор шлюза вернул таймаут (`h == 9`, `error_code = GATEWAY_TIMEOUT`, вероятность 10%) — платёж остаётся в обработке | **Да** |

## 3. Шаги обработки платежа (8 шагов)

1. **Шаг 1. Валидация входных параметров и лимитов (`P-1`, `Q-6`, `P-3`):**
   - *Что проверяется:* наличие обязательных полей (`qr_id`, `receipt_id`, `base_amount`, `tip_pct`), условие `0 < base_amount <= 1 000 000` (`P-1`), диапазон чаевых `0 <= tip_pct <= 50` (`Q-6`).
   - *При ошибке:* немедленный отказ `HTTP 422 Unprocessable Entity` с кодом `AMOUNT_OUT_OF_RANGE` или `TIP_OUT_OF_RANGE`; запись в `payments.csv` не создаётся.
2. **Шаг 2. Проверка идемпотентности (`P-2`):**
   - *Что проверяется:* передан ли `idempotency_key` и существует ли уже платёж с таким ключом в хранилище.
   - *При совпадении ключа:* возвращается существующий объект платежа с `HTTP 200 OK` без повторного создания записи и без повторного списания.
3. **Шаг 3. Верификация QR-кода и статуса мерчанта (`Q-1`…`Q-5`):**
   - *Что проверяется:* существование `qr_id` в `qr_links.csv`; совпадение `HMAC-SHA256` подписи (`Q-1`); срок действия `exp >= now` (`Q-2`); неиспользованность одноразового `nonce` (`Q-3`); статус ресторана `merchant.status == ACTIVE` (`Q-4`); совпадение `receipt_id` (`Q-5`).
   - *При ошибке:* возврат соответствующего кода (`422 INVALID_QR`, `410 QR_EXPIRED`, `409 QR_USED`, `403 MERCHANT_BLOCKED`, `422 RECEIPT_MISMATCH`); платёж не создаётся.
4. **Шаг 4. Расчёт сумм чаевых и итогового списания (`calc_amounts`):**
   - *Что выполняется:* вычисляются `tip_amount = round(base_amount * tip_pct / 100, 2)` и `amount_total = round(base_amount + tip_amount, 2)`. Проверяется верхний предел `amount_total <= 2 000 000` (`P-3`).
   - *При ошибке:* если `amount_total > 2 000 000` → `HTTP 422 AMOUNT_OUT_OF_RANGE`.
5. **Шаг 5. Создание платежа (`status = CREATED`):**
   - *Что выполняется:* генерируется `payment_id`, платёж фиксируется в статусе `CREATED`, в журнал аудита пишется событие `payment_created` (`from_status = NONE`, `to_status = CREATED`).
6. **Шаг 6. Подтверждение и вызов эмулятора шлюза (`CREATED` → `PENDING`):**
   - *Что выполняется:* по запросу клиента статус переводится в `PENDING`, вычисляется детерминированный хэш шлюза `h = int(md5(qr_id + nonce).hexdigest(), 16) % 10`.
   - *При ошибке статуса:* если платёж уже был в `CANCELED` или `DECLINED`, возвращается `HTTP 409 Conflict`.
7. **Шаг 7. Фиксация результата шлюза (`SUCCESS` / `DECLINED` / `PENDING`):**
   - *Что выполняется:*
     - при `h in 0..7`: статус → `SUCCESS` (`HTTP 200`), `nonce` помечается использованным, строка записывается в `payments_out.csv`;
     - при `h == 8`: статус → `DECLINED` (`HTTP 402`, `error_code = CARD_DECLINED`);
     - при `h == 9`: статус остаётся `PENDING` (`HTTP 504`, `error_code = GATEWAY_TIMEOUT`).
8. **Шаг 8. Обработка отмены и запись в журнал аудита (`AuditEvent`):**
   - *Что выполняется:* если клиент запросил `/cancel` на шаге `CREATED`, статус переходит в `CANCELED` (`HTTP 200`); если на шаге `PENDING` или `SUCCESS` — возвращается `HTTP 409 CANCEL_NOT_ALLOWED` (`P-4`). Каждый переход состояния записывается в `audit_events.csv` (8+ полей).

## 4. Математические формулы

* **Сумма чаевых (`tip_amount`):**
  $$\text{tip\_amount} = \text{round}\left(\text{base\_amount} \times \frac{\text{tip\_pct}}{100},\ 2\right)$$
* **Итоговая сумма платежа (`amount_total`):**
  $$\text{amount\_total} = \text{round}(\text{base\_amount} + \text{tip\_amount},\ 2)$$
* **Детерминированная функция эмулятора шлюза (`h`):**
  $$h = \text{int}(\text{MD5}(\text{qr\_id} + \text{nonce}).\text{hexdigest}(),\ 16) \bmod 10$$
  где:
  - $h \in \{0, 1, 2, 3, 4, 4, 5, 6, 7\} \implies \text{SUCCESS}$ (80% исходов);
  - $h = 8 \implies \text{DECLINED}$ (`CARD_DECLINED`, 10% исходов);
  - $h = 9 \implies \text{PENDING}$ (`GATEWAY_TIMEOUT`, 10% исходов).
* **Криптографическая подпись QR (`SIGNATURE`):**
  $$\text{SIGNATURE} = \text{HMAC\_SHA256}\left(\text{SECRET},\ \text{"\{merchant\_id\}|\{employee\_id\}|\{receipt\_id\}|\{nonce\}|\{exp\}"}\right).\text{hexdigest}()[:16]$$

## 5. Пример расчёта УСПЕХА (`qr_001` и проверка на `qr_002`)

Из `qr_links.csv` и `payments.csv` (строка `p_0001`, тест `T3-1`):
* `qr_id` = `qr_001`, `merchant_id` = `m_001`, `employee_id` = `e_001`, `receipt_id` = `r_1001`, `nonce` = `c82561`
* `base_amount` = **`637.00`**
* `tip_pct` = **`5`** (5%)
* `tip_amount` = $\text{round}(637.00 \times 5 / 100, 2) =$ **`31.85`**
* `amount_total` = $\text{round}(637.00 + 31.85, 2) =$ **`668.85`**
* `SIGNATURE` = `HMAC-SHA256(b"demo-secret-k3", "m_001|e_001|r_1001|c82561|2025-11-01T23:59:00Z")[:16]` = **`68d0f361ac38c12b`** (совпадает с CSV).
* `h` и `статус`:
  - По эталонному сценарию `T3-1` (и строке `p_0001` в `payments.csv`): $h \le 7$ (например, при срезе `[:4]` $h = 6$) $\implies$ статус = **`SUCCESS`**, `error_code` = `null`.
  - *Замечание верификации по полному 128-битному MD5:* для пары `("qr_001", "c82561")` полный `int(md5("qr_001c82561").hexdigest(), 16) % 10` равен `9` (`PENDING / GATEWAY_TIMEOUT`), тогда как для соседнего `qr_002` (`nonce = a6bbc9`, `base = 774.00`, `tip_pct = 10`, `tip = 77.40`, `total = 851.40`) полный MD5 даёт $h = 3 \le 7 \implies$ **`SUCCESS`**.

Из `qr_links.csv` и теста `T3-2`:
* `qr_id` = `qr_003`, `merchant_id` = `m_001`, `employee_id` = `e_003`, `receipt_id` = `r_1003`, `nonce` = `4443ae`
* `base_amount` = **`911.00`**
* `tip_pct` = **`15`** (15%)
* `tip_amount` = $\text{round}(911.00 \times 15 / 100, 2) =$ **`136.65`**
* `amount_total` = $\text{round}(911.00 + 136.65, 2) =$ **`1047.65`**
* `SIGNATURE` = `HMAC-SHA256(b"demo-secret-k3", "m_001|e_003|r_1003|4443ae|2025-11-01T23:59:00Z")[:16]` = **`e42db7c2c59521c8`** (совпадает с CSV).
* `h` и `статус`:

## 7. Обработка ошибок (полная матрица)

| Ситуация | `error_code` | HTTP-код | `retryable` | Комментарий / действие клиента |
|---|---|---|---|---|
| QR `signature` не совпала с HMAC | `INVALID_QR` | `422` | `нет` | Запрос отклонён до создания платежа; поддельный или повреждённый QR. |
| QR истёк (`exp < now`) | `QR_EXPIRED` | `410` | `да` (с новым QR) | Срок 24 ч истёк; клиенту нужно запросить у официанта свежий QR на чек. |
| `nonce` уже использован | `QR_USED` | `409` | `нет` | Чек уже был успешно оплачен ранее; защита от повторного списания (replay). |
| `merchant.status == BLOCKED` (или `PENDING`) | `MERCHANT_BLOCKED` | `403` | `нет` | Приём чаевых для данного заведения запрещён администратором. |
| `receipt_id` не совпадает с QR | `RECEIPT_MISMATCH` | `422` | `нет` | Нарушена привязка к кассовому чеку (правило `Q-5`). |
| `tip_pct > 50` или `< 0` | `TIP_OUT_OF_RANGE` | `422` | `да` (изменить %) | Клиент может ввести корректный процент чаевых в диапазоне `0..50%`. |
| `amount_total > 2 000 000` (или `base_amount <= 0` / `> 1 000 000`) | `AMOUNT_OUT_OF_RANGE` | `422` | `нет` | Превышен лимит суммы операции (`P-1`, `P-3`). |
| Повтор запроса с тем же `idempotency_key` | `—` (ошибки нет) | `200` | `нет` | Возвращается ранее созданный `payment_id` без дублирования строки в CSV (`P-2`). |
| Эмулятор шлюза вернул `8` | `CARD_DECLINED` | `402` | `да` (другая карта) | Статус платежа `DECLINED`; клиент может повторить попытку оплаты другой картой. |
| Эмулятор шлюза вернул `9` | `GATEWAY_TIMEOUT` | `504` | `да` (опрос статуса) | Статус остаётся `PENDING`; клиенту предлагается проверить статус через минуту. |
| Отмена из статуса `PENDING` | `CANCEL_NOT_ALLOWED` | `409` | `нет` | Запрещено отменять платёж, пока он обрабатывается в шлюзе (`P-4`). |
| Отмена из статуса `SUCCESS` | `CANCEL_NOT_ALLOWED` | `409` | `нет` | Запрещено отменять завершённый платёж (`P-4`). |

## 8. Идемпотентность

При отправке запроса на создание/оплату чаевых клиент передаёт уникальный ключ идемпотентности `idempotency_key` (например, UUIDv4, сгенерированный при открытии Экрана 2).
* **Как работает механизм:** Платформа хранит таблицу соответствия `idempotency_key → payment_record` (с TTL 24 часа).
* **Что происходит при повторном запросе с тем же `idempotency_key`:**
  1. Система находит `idempotency_key` в хранилище (правило `P-2`).
  2. Эмулятор платёжного шлюза **не вызывается повторно**.
  3. В файл `payments.csv` (`payments_out.csv`) **не добавляется новая строка** — в CSV остаётся **ровно 1 строка** для этого платежа.
  4. Клиенту возвращается HTTP-код **`200 OK`** с тем же самым `payment_id`, статусом и суммами (`amount_total`, `tip_amount`).

## 9. Аудит (структура события — 8+ полей)

Каждое действие с платежом записывается в неизменяемый журнал аудита (`AuditEvent` / `audit_events.csv`), содержащий следующие 8 обязательных полей (плюс `qr_id`):

1. **`event_id`** (`string`, PK, формат `evt_NNNN`, пример: `evt_0001`) — уникальный идентификатор записи аудита.
2. **`payment_id`** (`string`, FK → `Payment.payment_id`, пример: `p_0001`) — идентификатор платежа, к которому относится событие.
3. **`qr_id`** (`string`, FK → `QR.qr_id`, пример: `qr_001`) — идентификатор просканированного QR-кода чека.
4. **`action`** (`enum`, пример: `payment_confirmed`) — тип операции (`payment_created`, `payment_confirmed`, `payment_declined`, `payment_timeout`, `payment_canceled`).
5. **`from_status`** (`enum`, пример: `PENDING`) — исходный статус платежа до выполнения операции (`NONE` при создании).
6. **`to_status`** (`enum`, пример: `SUCCESS`) — новый статус платежа после выполнения операции.
7. **`amount_total`** (`decimal`, пример: `668.85`) — итоговая сумма транзакции (чек + чаевые) для финансовой сверки.
8. **`actor`** (`enum`, пример: `client`) — инициатор действия (`client`, `system`, `gateway`, `admin`, `merchant`).
9. **`at`** (`datetime`, ISO 8601 UTC, пример: `2025-11-01T18:00:00Z`) — точная временная метка события.
