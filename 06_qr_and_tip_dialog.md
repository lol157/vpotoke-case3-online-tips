# QR и диалоговая форма чаевых — кейс 3 «Онлайн-чаевые»

## 1. Payload QR (полная спецификация)

| Поле | Источник | Формат / Ограничение | Пример (из `qr_links.csv`) | Зачем нужно в системе |
|---|---|---|---|---|
| `qr_id` | генерируется сервером | `^qr_[0-9]{3}$` | `qr_001` | Уникальный первичный ключ QR-записи для короткой ссылки `https://tips.example/pay?qr=qr_001`. |
| `merchant_id` | `merchants.csv` | `^m_[0-9]{3}$`, `status=ACTIVE` | `m_001` | Идентификатор ресторана («Вкус-Сервис Тверская»), к которому относится чек. |
| `employee_id` | `employees.csv` | `^e_[0-9]{3}$` | `e_001` | Идентификатор официанта («Иванов И.»), которому начисляются чаевые. |
| `receipt_id` | кассовая система / сервер | `^r_[0-9]{4}$` | `r_1001` | Жёсткая привязка к кассовому чеку клиента (защита от подмены чека официантом, правило `Q-5`). |
| `nonce` | криптостойкий ГСЧ (`secrets.token_hex(3)`) | `^[a-f0-9]{6}$` (6 hex) | `c82561` | Одноразовый токен для защиты от повторного использования QR-кода (anti-replay, правило `Q-3`). |
| `exp` | `now + 24 часа` (UTC) | ISO 8601 `YYYY-MM-DDTHH:MM:SSZ` | `2025-11-01T23:59:00Z` | Срок жизни QR-кода (`TTL = 24 ч`); после истечения возвращается `410 Gone / QR_EXPIRED` (`Q-2`). |
| `signature` | `HMAC-SHA256(SECRET, payload)[:16]` | `^[a-f0-9]{16}$` (16 hex) | `68d0f361ac38c12b` | Криптографическая защита от модификации любого из полей QR-кода (`Q-1`). |

## 2. Подпись (ОБРАЗЕЦ И ПРОВЕРКА НА ДАННЫХ)

```python
import hmac
import hashlib
import os

# Секретный ключ загружается из переменной окружения (по умолчанию в демо-стенде b"demo-secret-k3")
SECRET = os.environ.get("TIPS_HMAC_SECRET", "demo-secret-k3").encode("utf-8")

def sign_qr_payload(merchant_id: str, employee_id: str, receipt_id: str, nonce: str, exp: str) -> str:
    payload = f"{merchant_id}|{employee_id}|{receipt_id}|{nonce}|{exp}"
    return hmac.new(SECRET, payload.encode("utf-8"), hashlib.sha256).hexdigest()[:16]

def verify_qr_signature(qr: dict) -> bool:
    expected = sign_qr_payload(
        qr["merchant_id"], qr["employee_id"], qr["receipt_id"], qr["nonce"], qr["exp"]
    )
    # Сравнение за константное время для защиты от timing-атак
    return hmac.compare_digest(expected, qr["signature"])
```

**Проверка на строке `qr_001` из `qr_links.csv`:**
- `payload` = `"m_001|e_001|r_1001|c82561|2025-11-01T23:59:00Z"`
- `HMAC-SHA256(b"demo-secret-k3", payload)` = `"68d0f361ac38c12b..."`
- Первые 16 символов: `"68d0f361ac38c12b"` — **100% совпадение с полем `signature` в `qr_links.csv`**.

## 3. Генерация QR и платёжной ссылки

### Пошаговый процесс генерации:

1. **Инициация запроса (Касса Мерчанта / Официант → Платформа):**
   При закрытии стола касса ресторана (или официант в ЛК) отправляет запрос на выпуск QR-кода, передавая `merchant_id`, `employee_id`, `receipt_id` и базовую сумму чека `base_amount`.
2. **Валидация бизнес-правил при генерации (Платформа):**
   - Проверяется, что мерчант существует в `merchants.csv` и имеет статус `merchant.status == "ACTIVE"` (если `BLOCKED` или `PENDING` → отказ `403 MERCHANT_BLOCKED`, правило `Q-4`).
   - Проверяется, что сотрудник `employee_id` существует в `employees.csv` и привязан именно к этому `merchant_id` (`employee.merchant_id == merchant.merchant_id`), а его `payment_details` заданы в маскированном формате `****NNNN`.
   - Проверяется уникальность номера чека `receipt_id` в рамках данного мерчанта и корректность суммы чека (`0 < base_amount <= 1 000 000`, правило `P-1`).
3. **Криптографическая генерация параметров (Платформа):**
   - Присваивается порядковый или уникальный `qr_id` (например, `qr_001`).
   - Генерируется криптостойкий одноразовый `nonce` длиной 6 hex-символов (`secrets.token_hex(3)`, например `c82561`).
   - Вычисляется время истечения срока действия `exp = now_utc + 24 hours` в формате ISO 8601 (`YYYY-MM-DDTHH:MM:SSZ`).
   - Вычисляется подпись `signature = HMAC-SHA256(SECRET, f"{merchant_id}|{employee_id}|{receipt_id}|{nonce}|{exp}")[:16]`.
4. **Сохранение в хранилище (Платформа → `qr_links.csv` / БД):**
   Запись `(qr_id, merchant_id, employee_id, receipt_id, nonce, exp, signature)` сохраняется в `qr_links.csv`, а событие генерации логируется в аудит.
5. **Формирование платёжной ссылки и QR-изображения (Платформа → Чек):**
   Формируется короткая платёжная ссылка `https://tips.example/pay?qr={qr_id}` (например, `https://tips.example/pay?qr=qr_001`), кодируется в матричный QR-код (стандарт ISO/IEC 18004, уровень коррекции ошибок M) и печатается в подвале кассового чека клиента.

## 4. Диалоговая форма выбора чаевых (4 экрана)

Диалоговая веб-форма открывается на смартфоне клиента сразу после сканирования QR-кода (без установки приложений):

### Экран 1. Приветствие и верификация чека (`GET /api/v1/qr/{qr_id}`)
- **Назначение:** показать клиенту, кому и за какой чек он оставляет чаевые, убедиться в валидности QR.
- **Проверки на входе:** `Q-1` (HMAC-подпись), `Q-2` (`exp >= now`), `Q-3` (`nonce` не использован), `Q-4` (`merchant.status == ACTIVE`).
- **Отображаемые данные:**
  - Название заведения: **«Вкус-Сервис Тверская»** (`merchant.name`)
  - Ваш официант: **Иванов И.** (`employee.name`)
  - Номер чека: **#r_1001** (`receipt_id`)
  - Сумма по чеку: **637.00 ₽** (`base_amount`)
- **Действия:** кнопка **«Продолжить к выбору чаевых →»**. (Если QR невалиден или истёк — сразу отображается экран ошибки `422 INVALID_QR` или `410 QR_EXPIRED`).

```text
+------------------------------------------+
|         ВКУС-СЕРВИС ТВЕРСКАЯ             |
|------------------------------------------|
|  Ваш официант:   Иванов И.               |
|  Чек №:          r_1001                  |
|  Сумма счёта:    637.00 ₽                |
|                                          |
|      [ Продолжить к выбору чаевых ]      |
+------------------------------------------+
```

### Экран 2. Выбор процента чаевых (`POST /api/v1/tips`)
- **Назначение:** интерактивный выбор размера вознаграждения с мгновенным пересчётом итоговой суммы.
- **Варианты выбора:** быстрые пресеты **`0%`**, **`5%`**, **`10%`**, **`15%`**, **`20%`** или поле ввода своего процента/суммы (валидация по правилу `Q-6`: строго `0% <= tip_pct <= 50%`, иначе подсветка ошибки `TIP_OUT_OF_RANGE`).
- **Динамический расчёт на экране (на примере `qr_001`, выбор `5%`):**
  - Сумма чека (`base_amount`): `637.00 ₽`
  - Чаевые (`tip_amount = round(637.00 * 5 / 100, 2)`): `31.85 ₽`
  - **Итого к оплате (`amount_total`):** **`668.85 ₽`**
- **Действия:** при нажатии кнопки **«Оплатить 668.85 ₽»** клиентское приложение генерирует уникальный `idempotency_key` (UUIDv4) и отправляет `POST /api/v1/tips`. Платформа проверяет `P-1`..`P-3` и создаёт платёж в статусе **`CREATED`**.

```text
+------------------------------------------+
|  Выберите размер чаевых для Иванова И.   |
|------------------------------------------|
|   [ 0% ]  [*5%*]  [ 10% ] [ 15% ] [ 20% ]|
|   Другой % (0..50%): [  5  ] %           |
|------------------------------------------|
|  Сумма по чеку:                 637.00 ₽ |
|  Чаевые (5%):                   +31.85 ₽ |
|  ИТОГО К ОПЛАТЕ:                668.85 ₽ |
|                                          |
|          [ Оплатить 668.85 ₽ ]           |
+------------------------------------------+
```

### Экран 3. Подтверждение оплаты (`POST /api/v1/payments/{id}/confirm` или `/cancel`)
- **Назначение:** финальная проверка параметров транзакции перед списанием средств в платёжном шлюзе и возможность легальной отмены.
- **Отображаемые данные:**
  - ID платежа: `p_0001` (статус `CREATED`)
  - Получатель: `Вкус-Сервис Тверская / официант Иванов И.`
  - Сумма чека: `637.00 ₽` | Чаевые (5%): `31.85 ₽` | **Итого: `668.85 ₽`**
- **Действия:**
  - Кнопка **«Подтвердить оплату»** → вызывает `POST /api/v1/payments/{id}/confirm` (платёж переходит в `PENDING` и отправляется в эмулятор шлюза).
  - Кнопка **«Отменить»** → вызывает `POST /api/v1/payments/{id}/cancel` (пока статус `CREATED`, платёж безопасно переводится в `CANCELED`).

```text
+------------------------------------------+
|          ПОДТВЕРЖДЕНИЕ ОПЛАТЫ            |
|------------------------------------------|
|  Платёж:         p_0001 (CREATED)        |
|  Сумма чека:     637.00 ₽                |
|  Чаевые (5%):     31.85 ₽                |
|  ИТОГО СПИСАНИЕ: 668.85 ₽                |
|                                          |
|  [ Подтвердить оплату ]    [ Отменить ]  |
+------------------------------------------+
```

### Экран 4. Результат операции
Отображает финальный статус ответа от платёжного шлюза:
- **Сценарий А — Успех (`status = SUCCESS`, HTTP 200, `h in 0..7`):**
  *«Спасибо! Чаевые (31.85 ₽) успешно отправлены официанту Иванову И. Чек #r_1001 оплачен (668.85 ₽)»*. Одноразовый `nonce` погашен.
- **Сценарий Б — Отказ шлюза (`status = DECLINED`, `error_code = CARD_DECLINED`, HTTP 402, `h == 8`):**
  *«Оплата не прошла (отказ банка по карте). Пожалуйста, попробуйте другой способ оплаты»*. Доступна кнопка «Попробовать снова» (`retryable = true`).
- **Сценарий В — Таймаут шлюза (`status = PENDING`, `error_code = GATEWAY_TIMEOUT`, HTTP 504, `h == 9`):**
  *«Платёж обрабатывается банком. Пожалуйста, не оплачивайте повторно — проверьте статус через минуту»* (защита от двойного списания за счёт `idempotency_key`).
- **Сценарий Г — Отменён клиентом (`status = CANCELED`, HTTP 200):**
  *«Платёж отменён по вашему запросу. Средства не списывались»*.

## 5. Критерий приёмки

- [x] Payload QR содержит 6 подписываемых полей (+ `qr_id`) с подробным объяснением
- [x] Подпись `HMAC-SHA256` (не plain hash), сверена с эталонным `qr_links.csv`
- [x] TTL QR = 24 ч, `nonce` одноразовый (6 hex)
- [x] Описаны все 4 экрана диалога с проверками и состояниями
- [x] Указаны проверки при генерации QR (`merchant.status = ACTIVE`, принадлежность официанта, уникальность `receipt_id`)
